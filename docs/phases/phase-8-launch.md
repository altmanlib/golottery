# 上线与现场兜底

## 1. 目标与范围

把已完成的 API 与 Web 部署到一套可回滚的环境，并给出现场在网络故障时仍能完成抽奖的兜底。

做：

1. API 镜像与发布脚本
2. PostgreSQL 备份与恢复步骤
3. Nginx 反向代理、HTTPS 与 SSE 配置
4. Web 静态文件发布
5. 不依赖服务端的大屏兜底页
6. 坐标保留与清理任务

不做：

- 多机水平扩展、Redis、消息队列
- 在线支付、发票、短信
- 每组织独立数据库
- 自动扩容

## 2. 现状与约束

| 项 | 现状 |
| --- | --- |
| API | 单进程 Go 二进制，默认 `127.0.0.1:5568` |
| Web | Vite 静态产物 |
| 数据 | 一台 PostgreSQL |
| 实时 | SSE 长连接 |

首发只保证一场约 800 人、签到峰值 100 请求/秒的容量目标。压测不通过时先限流，不改成分布式。

## 3. 原则

1. 同一版本可回滚到上一份镜像和上一份 Web 产物
2. 数据库迁移只向前追加
3. 备份先于第一次生产写入
4. 兜底页不连接生产 API，也不包含访问凭证
5. 清理坐标时保留签到结果、距离和原因

## 4. 方案

### 4.1 发布

- API 使用现有 Dockerfile 构建镜像，版本取 `golottery-api/VERSION`
- Web 构建 `dist`，以时间戳加提交号保存版本目录，当前版本用软链接切换
- 生产配置只通过环境变量注入。`SESSION_SECRET`、数据库口令和微信密钥不进镜像
- Nginx 将 `/api`、`/healthz`、`/readyz`、`/openapi.json` 反代到 API；其余路径回落 `index.html`
- SSE 路径关闭代理缓冲，读超时大于心跳间隔

发布文档写明顺序：备份、迁移、启动 API、检查 `/readyz`、切换 Web、回滚。

### 4.2 数据保护

- 每天逻辑备份 PostgreSQL，至少保留 7 份
- 恢复演练用独立库，不覆盖生产库
- `checkin_attempts.lat` 与 `lng` 在活动 `closed` 30 天后清空
- 清理由 API 每日任务执行，写入运行日志；不删除尝试记录

### 4.3 现场兜底

组织管理员在活动开始前导出名单、奖项和已签到状态。兜底页是一个静态 HTML：

- 本地打开，不访问网络
- 导入导出的 JSON 或 xlsx
- 使用浏览器加密随机源选人
- 结果导出为文件，活动后由管理员手工对照，不自动回写数据库

兜底结果与服务端结果没有合并协议。现场一旦改用兜底页，本场后续不再回到服务端抽奖。

### 4.4 验收

| 项目 | 标准 |
| --- | --- |
| 回滚 | 切换回上一版本后 `/readyz` 为 200 |
| 恢复 | 备份可恢复到独立库 |
| SSE | Nginx 后心跳不断开 |
| 清理 | 坐标清空后签到状态仍可导出 |
| 兜底 | 断网状态下可从本地文件完成一次抽奖并导出 |

## 5. 明确不做

- 多区域容灾
- 兜底结果自动导入
- 零停机迁移

## 6. 完成定义

- 发布与恢复步骤可按文档执行
- 生产配置没有写入仓库
- 兜底页可在无网络的浏览器中完成一次抽奖
